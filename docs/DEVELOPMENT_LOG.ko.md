# Loadit 개발기
## 다운로드의 속도와 웹의 기억을 하나로 묶는 실험

> **프로젝트:** Loadit / 로드잇  
> **저장소:** https://github.com/hslcrb/loadit  
> **기록 기준:** 2026년 11월 21일 (KST)  
> **현재 버전:** Manifest `0.2.0`  
> **기록의 성격:** 실제 소스·커밋을 근거로 한 기술 개발기. 설계 의도, 구현 사실, 테스트 주장, 미검증 영역을 구분한다.  
> **사용 기술:** HTML, CSS, JavaScript, Chrome Extensions Manifest V3 및 필수 JSON 매니페스트

## 0. 이 개발기를 읽는 방법

이 문서는 흔한 홍보용 기능 목록이 아니다. 무엇을 만들려고 했는지, 어떤 구조를 선택했는지, 실제 소스가 어디까지 구현되어 있는지, 성능·보안·호환성 측면에서 무엇을 더 확인해야 하는지를 **나중에 다시 개발을 이어갈 수 있을 정도로** 남기기 위한 기록이다.

문장에는 다음 네 가지 층위가 있다.

- **[요구]** 사용자 요청에서 확정된 제품 방향. 코드의 완료 여부와 관계없다.
- **[구현]** `main`에 실제로 존재하는 코드·파일·경로에 근거한 사실.
- **[검증]** 확인 방법과 결과가 분명한 범위. 구체적인 실행 증거가 없으면 검증 완료라고 쓰지 않는다.
- **[과제]** 코드가 아직 없거나, 있더라도 브라우저에서 신뢰할 만한 재현 시험이 남은 부분.

특히 **코드가 GitHub에 올라갔다 = Chrome에서 설치·실행된다 = 실제 웹사이트를 정확히 복원한다**는 등식은 성립하지 않는다. 서로 다른 단계다. 이 구분을 이번 개발기의 중요한 원칙으로 삼는다.

### 핵심 요구를 한 문장으로

> GitHub를 포함한 여러 저장 경로에서 **빠르게 저장하고 다운로드하는 도구**와, 여러 웹페이지를 **하나의 HTML에 보존하고 JavaScript로 오프라인 페이지 전환하는 도구**를 독립 모듈로 만들어 하나의 제품 **Loadit**으로 통합한다.

GitHub는 선택 가능한 저장 대상 중 하나일 뿐이며, 일반 파일 다운로드·웹사이트 보존은 GitHub 로그인 없이 동작하는 것이 목표다.

## 1. 프로젝트가 탄생한 배경

### 1.1 서로 다른 두 불편

첫 번째 불편은 **저장의 마찰**이다. 자료를 읽고 있거나 좋은 생각이 떠올랐을 때, 별도 서비스로 이동하고 저장소를 찾고 파일 이름을 작성하고 수동으로 붙여넣는 과정은 작지만 반복된다. 메모를 바로 로컬 파일로 내보내거나 GitHub의 지정한 경로에 새 파일로 남길 수 있다면 작업 흐름의 이탈을 줄일 수 있다. 같은 맥락으로 링크·이미지·미디어 등 웹상에서 다운로드 가능한 파일도 하나의 확장에서 다루려 했다.

두 번째 불편은 **웹페이지의 휘발성**이다. 단일 시점의 한 장을 저장하는 것으로 끝나면 하위 페이지 탐색, API가 채운 콘텐츠, 페이지 사이 이동 관계는 쉽게 사라진다. 그래서 저장 단위를 단일 DOM 한 장에서 여러 페이지의 묶음으로 키우고, **결과물만은 파일 하나로 유지**하고자 했다.

두 아이디어의 공통분모는 '웹에서 만난 정보를 내 손에 남기는 과정'이지만 기술 성격은 다르다. 그래서 구현은 하나의 팝업으로 묶되 코드는 **Download/Quick Save**와 **Archive/Replay** 경계로 분리했다.

### 1.2 사용자가 확정한 가장 중요한 기술 조건

- 프로젝트 이름은 **Loadit(로드잇)**.
- 저장소는 **`hslcrb/loadit`**.
- Chrome 확장 프로그램 형식으로 사용.
- **HTML, CSS, JavaScript만** 사용. 필수 확장 설정 파일인 `manifest.json`은 예외.
- 아카이버 산출물은 페이지별 파일 묶음이나 서버에 기대지 않고 **단일 HTML 파일**.
- 저장된 여러 페이지의 선택·전환은 **JavaScript**로 구현.
- 다운로드 확장은 GitHub만 대상으로 하는 것이 아니라 일반 URL과 웹 리소스까지 포괄.
- 이전 아이디어에 등장한 `fetch` / XHR / WebSocket 동적 데이터의 보존·재생도 발전 방향에 포함.

여기서 마지막 항목은 가장 어렵다. 화면을 정적으로 보존하는 일과 웹앱의 **실행 환경을 다시 돌리는 일**은 깊이가 다른 문제이기 때문이다.

### 2.1 첫 구현 — 사용할 수 있는 뼈대 세우기

초기 저장소가 사실상 비어 있었으므로 프레임워크를 먼저 고르는 대신, 확장 로드에 필요한 최소 경로부터 구성했다.

1. `manifest.json`으로 Manifest V3 권한·진입점 선언.
2. `popup.html`/`popup.css`/`popup.js`로 세 작업 탭 구성.
3. `background.js`로 다운로드·우클릭 메뉴·텍스트 저장·GitHub API 연결.
4. `offscreen.html`/`offscreen.js`로 Blob URL 다운로드 처리.
5. `archive.js`로 동일 출처 링크 탐색과 DOM·자산 캡처.
6. `viewer.html`로 데이터가 내장된 한 HTML 파일 내부의 탐색 UI 구현.
7. `test-site`로 최소 두 페이지의 샘플 마련.

이 순서는 UI만 화려하고 파일은 나오지 않는 상태를 피하기 위한 것이다. Loadit의 존재 이유는 **저장 결과물을 실제 파일로 가져가는 것**이기 때문이다.

### 2.2 성능 보강 — 무제한 수집보다 예측 가능한 상한

이미지를 하나씩 기다리면 실패하는 리소스마다 수 초의 지연이 누적될 수 있다. 따라서 페이지 이미지 수집에 **최대 6개 worker 수준의 제한적 병렬 처리**를 적용했다. 파일 전체 크기가 무한히 커지는 것을 막기 위해 HTML 데이터 전체에 상한도 두었다.

이후 네트워크 데이터·스크립트 기록이 추가되면서 현재 `archive.js`의 전체 상한은 약 **75MiB**다. 초기 성능 보강 단계의 상한과 현재 코드의 상한은 동일하지 않다. 이 숫자를 '일반적인 사이트가 75MiB 안에서 완벽히 저장된다'는 뜻으로 해석해서는 안 된다.

### 2.3 네트워크 기록 및 재생 — 정적 스냅샷의 다음 단계

정적 DOM만 저장하면 페이지가 처음 뜰 때 화면을 채운 API 응답이나 실행 중의 WebSocket 메시지는 사라질 수 있다. 그래서 `capture.js`를 추가해 **Chrome DevTools Protocol(CDP)** 계층에서 브라우저가 수신한 일부 HTTP 응답·WebSocket 프레임을 기록하도록 했다.

저장된 HTML 안에는 렌더링된 페이지뿐 아니라 **기록된 원본 스크립트 일부와 네트워크 응답 데이터**도 포함된다. 재생은 안전·호환성을 위해 기본 꺼짐이며, 사용자가 뷰어에서 실험 모드를 켜야 한다.

## 3. 모듈별 설계 및 현재 소스 구조

```text
                      ┌────────────────────────────────────┐
                      │ Chrome 확장 UI: popup.html/css/js │
                      │ Download │ Site Archive │ Quick Note │
                      └──────────────────┬─────────────────┘
                                         │ chrome.runtime 메시지
                                         ▼
                          ┌────────────────────────┐
                          │ background.js (MV3 SW) │
                          └───┬─────────┬────────┬─┘
                              │         │        │
                    chrome.downloads    │      GitHub REST API
                              │         │        │
                        Offscreen Blob  │    Contents PUT / 조회
                              │         │
                              │      archive.js
                              │      ├─ URL queue / 탐색 제어
                              │      ├─ DOM snapshot
                              │      └─ capture.js / CDP 기록
                              │              │
                              └──────┬───────┘
                                     ▼
                        viewer.html 템플릿 + JSON
                                     │
                                     ▼
                     하나의 오프라인 HTML 파일
                         ├─ 페이지 목록·검색
                         ├─ iframe.srcdoc 전환
                         └─ 선택적 fetch/XHR/WS Replay
```

이 구조는 하나의 프로젝트 안에서도 **각 기능의 실패 범위를 줄이기 위해** 설계했다. 예를 들어 GitHub API가 실패했다고 이미 내려받은 파일이 사라져서는 안 되고, 한 페이지의 자산 캡처가 실패했다고 다른 페이지 기록까지 반드시 폐기할 필요는 없다.

### 3.1 `manifest.json`

Chrome 확장 프로그램의 선언부다. `manifest_version: 3`, 팝업 위치, 백그라운드 서비스 워커, 필요한 권한을 정의한다.

권한을 성격별로 나누어 보면 다음과 같다.

| 권한 | 도입 이유 | 주의 |
| --- | --- | --- |
| `downloads` | URL·Blob 다운로드 및 상태 제어 | 파일 저장은 브라우저 정책의 적용을 받음 |
| `contextMenus` | 링크·이미지·미디어·선택 텍스트의 빠른 실행 | 브라우저별 동작 차이 |
| `tabs` / `activeTab` | 현재 주소·임시 캡처 탭 관리 | 다른 탭의 의도치 않은 변경 방지 필요 |
| `scripting` | DOM에서 다운로드 후보 탐색 및 스냅샷 실행 | 사용자의 사이트 접근 범위 안에서만 |
| `offscreen` | Service Worker에서 만들기 어려운 Blob URL 작업 | 임시 객체의 해제와 수명 관리 필요 |
| `storage` | 선택 텍스트·설정·작업 상태 | 민감정보 저장과 구분 |
| `debugger` | CDP Network/Page 캡처 | 광범위한 접근 능력을 가지므로 특히 주의 |
| GitHub 호스트 권한 | GitHub 공식 API 호출 | 접근 토큰 권한 최소화 |
| 선택적 HTTP(S) 호스트 권한 | 사용자가 선택한 사이트 캡처 | 도메인별 승인 필요 |

**보안적으로 중요한 점:** `debugger` 권한은 일반 다운로드 관리보다 훨씬 강력하다. 현재 코드가 사용할 때만 연결하고 해제하도록 설계됐다는 사실과, 확장 프로그램 자체가 그 권한을 요청한다는 사실을 함께 설명해야 한다.

### 3.2 `popup.html`, `popup.css`, `popup.js`

UI는 세 탭으로 나뉜다.

- **다운로드:** URL 직접 입력, 파일 후보 스캔, 체크박스 선택 다운로드, 최근 다운로드 목록.
- **사이트 보존:** 시작 URL, 최대 페이지 수, 탐색 깊이, 작업 진행 상태.
- **빠른 메모:** 텍스트 영역, 로컬 TXT 저장, GitHub 경로·PAT 입력, 저장소·폴더 탐색.

`popup.js`는 사용자 액션을 받아 `chrome.runtime.sendMessage`로 백그라운드에 전달한다. 다운로드 진행 현황, 저장소 탐색 결과, 아카이브 상태는 인터페이스에서 별도 갱신한다. 이 구조는 UI가 네트워크 캡처·파일 조립까지 직접 맡지 않게 하려는 선택이다.

UI에는 고유의 상태가 있지만 **UI 화면에 표시된 상태가 모든 작업의 실제 완료 증거는 아니다.** 예를 들어 다운로드 API가 ID를 반환하면 시작 요청이 접수된 것이고, 파일 쓰기·검증 완료까지 보장하는 것은 아니다.

### 3.3 `background.js`

메시지 분배와 작업 실행을 담당한다. 현재 주요 요청 타입은 다음과 같다.

```text
DOWNLOAD_URL        HTTP(S) 파일 URL 다운로드 시작
COLLECT_LINKS       현재 DOM에서 링크·이미지·미디어 후보 수집
DOWNLOADS           Chrome 다운로드 기록 조회
DOWNLOAD_CONTROL    pause / resume / cancel / show
SAVE_TEXT           TXT를 Blob으로 만들어 다운로드
GITHUB_NOTE         GitHub Contents API로 신규 텍스트 파일 생성
GITHUB_BROWSE       저장소 목록·폴더 경로 조회
ARCHIVE_START       아카이빙 시작
ARCHIVE_STATUS      아카이빙 진행 상태 읽기
LAST_SELECTION      최근 선택 텍스트 조회
```

백그라운드는 `importScripts("capture.js", "archive.js")`로 기록기와 아카이버를 연결한다. `archiveRunning` 플래그는 동시에 중복 작업을 시작하지 않도록 하는 간단한 장치다.

**현재 해결되지 않은 중요한 지점:** MV3 서비스 워커는 계속 살아 있는 Node 서버가 아니다. 구현의 비동기 작업이 브라우저의 워커 수명과 중단에 어떻게 반응하는지, 페이지 수가 많을 때 중단 후 복구가 가능한지는 실환경 테스트가 필요하다. `archiveRunning`만으로 지속성·복구성을 보장하지 않는다.

### 3.4 `offscreen.html` / `offscreen.js`

Service Worker에서는 DOM과 일부 Web API를 직접 다루지 못한다. 그래서 텍스트와 HTML을 `Blob`으로 만들고 `URL.createObjectURL`로 다운로드할 수 있도록 **Offscreen Document**를 둔다.

```text
background.js
   └─ OFFSCREEN_BLOB(content, mime)
           ↓
      offscreen.js
           ↓
      Blob URL 발급
           ↓
      chrome.downloads.download()
           ↓
      완료/중단 이벤트 관찰
           ↓
      OFFSCREEN_RELEASE → URL.revokeObjectURL()
```

브라우저 메모리에 만들어진 객체 URL을 해제하지 않으면 불필요한 자원 누적 위험이 있다. 현재 완료/중단 이벤트를 이용한 해제 경로가 존재한다. 그러나 브라우저 비정상 종료, 이벤트 누락, 장시간 열린 offscreen document까지 포함한 **자원 누수 시험을 마쳤다고 볼 수는 없다**.

## 4. Download — 파일을 빠르게 저장하는 쪽

### 4.1 범용 URL 다운로드

`downloadURL`은 URL을 `URL` 객체로 해석하고 **`http:` 또는 `https:`**만 허용한 뒤 `chrome.downloads.download`에 전달한다. 이름이 지정되면 파일명과 하위 폴더를 가공해 다운로드 API에 보낸다.

이 설계의 장점은 별도 HTTP 파일 전송 스택을 만드는 대신 Chrome이 이미 제공하는 다운로드 처리·상태·파일 저장 동작을 활용한다는 점이다. 반면 IDM류 다운로드 관리자에서 기대할 수 있는 **다중 세그먼트 고속 가속·부분 파일 병합·다중 서버 미러링**은 현재 코드에 없다.

### 4.2 다운로드 후보를 찾는 방법

`COLLECT_LINKS`는 현재 탭에서 다음 DOM을 살핀다.

- `a[href]`: 다운로드 속성이 있거나 일반적인 파일 확장자로 보이는 링크
- `img`: `currentSrc`를 활용할 수 있는 이미지
- `video`, `audio`, `source`: 접근 가능한 미디어 URL

동일 URL은 중복 제거하고, 후보 수집은 최대 180개, 한 번에 선택 다운로드할 수 있는 수는 최대 30개로 제한한다.

이 기능은 **DOM에 드러난 리소스를 쉽게 선택한다**는 목적에 맞는다. 별도 네트워크 스니퍼가 아니므로 서버가 JS를 통해 동적으로 만드는 일회성 다운로드, 블롭 URL, 내부 POST API, 다운로드 토큰 등을 모두 찾지는 못한다.

### 4.3 브라우저 다운로드 목록 제어

`chrome.downloads.search`에서 최근 기록을 조회하고, 진행 중이면 `pause`·`resume`·`cancel`, 완료되었다면 `show`를 요청한다. 이는 서버·브라우저가 허용하는 범위에서만 성공한다.

- 멈추기와 재개하기는 동일하지 않다.
- 재개하려면 서버가 해당 다운로드 흐름을 지원해야 할 수 있다.
- 시작 API가 ID를 주었다고 파일 다운로드가 완성됐다고 보고하지 않는다.
- 다운로드 가능한 파일의 크기·무결성·완료 여부를 개별 검증하는 테스트가 필요하다.

### 4.4 우클릭 빠른 실행

`contextMenus`로 링크·이미지·미디어·현재 페이지 주소에 대한 다운로드 진입점을 둔다. 선택한 텍스트는 로컬 TXT로 저장하거나, GitHub 저장 화면으로 넘길 수 있다. **우클릭 하나로 모든 파일이 GitHub에 올라가는 구조는 아직 아니다.** 일반 파일은 로컬 다운로드로, GitHub는 텍스트 신규 생성으로 분기한다.

## 5. Quick Save — 생각을 파일로 바꾸는 쪽

### 5.1 로컬 텍스트 저장

텍스트 영역에서 직접 작성하거나 웹페이지에서 선택한 글을 로컬 `.txt`로 저장한다. 선택 텍스트는 `chrome.storage.session`의 `loaditSelection`으로 임시 전달한다.

장점은 메모를 만들기 위해 새로운 데이터베이스·클라우드 계정을 열 필요가 없다는 점이다. 저장된 파일 자체가 결과물이다.

### 5.2 GitHub 신규 파일 생성

GitHub 기능은 REST API의 `PUT /repos/{owner}/{repo}/contents/{path}`를 사용한다. 요청 본문에는 커밋 메시지와 Base64로 인코딩한 UTF-8 텍스트가 들어간다. 기존 파일 SHA를 보내지 않으므로 **기존 경로 덮어쓰기가 아닌 신규 파일 생성**에 해당한다.

현재 로직은 다음을 수행한다.

1. `owner/repo` 형식 검사.
2. 입력 파일 경로의 기본 검증.
3. 빈 본문·큰 본문 차단(900KiB 이하 텍스트).
4. 사용자가 제공한 PAT로 GitHub API 호출.
5. 성공 응답의 파일 URL 표시.

또한 `GET /user/repos`와 저장소 Contents API를 이용하여 최대 100개 수준의 저장소/폴더 결과를 UI에 보여 주도록 했다. **전체 페이지네이션·모든 계정 저장소 전수 조회는 미구현**이다.

### 5.3 토큰·개인정보에 관한 설계 판단

토큰을 Chrome 로컬 설정에 저장하는 기능은 두지 않았다. 설정에는 선택한 저장소 이름과 경로만 저장할 수 있다. 그러나 이 사실만으로 토큰 유출 위험이 0이 되지는 않는다. 토큰은 입력 동안 메모리에 존재하고 공식 GitHub API로 전송된다. 최소 권한·최소 범위·토큰 만료 정책이 중요하다.

또한 선택 텍스트나 네트워크 수집 데이터가 개인 정보일 수 있으므로, **GitHub 공개 저장소에 올리는 파일은 사용자 자신이 공개 범위를 확인해야 한다**. 저장 기능은 내용 자체를 자동 익명화하거나 비밀을 걸러내지 않는다.

## 6. Archive — 여러 페이지를 한 파일로 만든 과정

### 6.1 저장 단위부터 재정의

일반적인 웹 아카이브는 페이지별 HTML과 asset 폴더, 서버 혹은 ZIP 형태를 사용할 수 있다. 이번 요구에서는 **결과 파일 하나**가 가장 우선하는 제약이었다. 그래서 `viewer.html`을 껍데기, `pages[]`를 데이터, `iframe.srcdoc`를 페이지 출력 창으로 삼았다.

```text
단일 HTML 파일
├─ 뷰어 UI: 페이지 목록 / 검색 / 이전·다음
├─ 내장 JSON:
│   ├─ pages[0] = HTML + JS sources + Network records
│   ├─ pages[1] = HTML + JS sources + Network records
│   └─ ...
└─ 내장 JavaScript:
    ├─ 페이지 색인 및 URL 대응표
    ├─ 현재 페이지 표시
    ├─ 링크 클릭 → 저장된 페이지 번호 탐색
    └─ 실험 모드의 HTTP/WS 기록 재생
```

이 구조에서는 페이지 선택 시 다른 HTML 파일을 불러오는 것이 아니라, **이미 한 파일에 들어 있던 HTML 문자열을 선택해 보여 준다**. 로컬 파일 옆에 별도 서버가 없어도 뷰어 UI가 작동하도록 설계됐다.

### 6.2 URL 탐색 정책

현재 `archive.js`에는 방문할 URL 큐, 방문 집합, 페이지별 깊이, 최대 페이지 수가 있다. 시작 URL에서 링크를 발견하고, 같은 origin이며 방문하지 않은 URL을 큐에 추가하는 방식이다. `#hash`는 방문 중복 판정에서 제거한다.

이 방법은 웹사이트 구조를 부분적으로 따라가기 적합하지만 다음은 별도 고려가 필요하다.

- JavaScript 이벤트로만 이동하는 화면이나 가상 라우트
- 검색 결과·무한 스크롤·버튼 클릭 후에만 등장하는 URL
- query string 차이로 만들어지는 중복 페이지
- 로그인·권한 상태별 다른 결과
- 여러 출처에 걸친 서비스
- 무한 생성형 URL 및 탐색 폭주

따라서 현재 수집은 사용자 설정에 따른 **제한된 동일 출처 링크 탐색**이지 '도메인의 모든 페이지를 완전 발견'하는 크롤러가 아니다.

### 6.3 임시 탭을 열어 실제 브라우저가 렌더링하도록 함

URL마다 `about:blank` 임시 탭을 만든 뒤 네트워크 기록 계층을 연결하고, 해당 URL로 이동한다. 페이지 로드 완료 이벤트 후 짧게 기다리고 스냅샷을 시도한다.

브라우저가 실제로 실행한 DOM을 저장하려는 선택이므로 단순 HTTP `fetch`만으로 HTML 원문을 내려받는 것과 다르다. 그러나 **로드 완료**는 **모든 비동기 데이터가 도착했고 모든 이미지가 준비되었다**는 의미가 아니다. 동적 페이지의 안정화 여부를 확인하는 별도 조건이 필요하다.

### 6.4 `loaditSnapshot`의 주요 일

`document.documentElement.cloneNode(true)`로 현재 렌더링된 DOM을 복제한다. 이후 저장본이 독립적으로 표시될 수 있도록 여러 작업을 수행한다.

- `a[href]`를 정규화하여 추후 방문 후보로 수집
- 외부 스타일시트의 CSS를 읽어 `<style>`로 옮기려 시도
- CSS `url(...)`에 참조된 리소스를 Data URL로 변환 시도
- 이미지는 `currentSrc` 중심으로 Data URL 내장 시도
- 미디어는 크기 제한 안에서 가능한 `src`를 내장
- 캔버스는 읽을 수 있을 경우 이미지로 보존 시도
- SVG의 이미지 참조도 가능하면 내장
- 일부 폼 필드의 화면 표시 상태를 복제
- 외부 스크립트·인라인 스크립트의 소스 중 가능한 것을 **비활성 템플릿**과 별도 기록으로 보존
- 스크립트 이벤트 속성·불필요한 외부 참조를 제거하는 방향으로 재구성

정적 아카이브에는 단순 HTML 텍스트가 아니라 **HTML이 참조했던 자산을 파일 내부 데이터로 옮기는 과정**이 필요하다. 이 과정이 품질의 핵심이고, 동시에 CORS·중복·성능·보안 문제가 집중되는 위치다.

### 6.5 이미지·스타일을 '다 받은 것처럼' 말하지 않기로 한 이유

다음 상황에서는 리소스가 누락될 수 있다.

- 서버가 CORS나 인증 조건으로 리소스를 제공하지 않는 경우
- 외부 CDN의 접근 정책이 다르거나 자산 URL이 만료된 경우
- 브라우저 화면에서 아직 로드되지 않은 lazy 이미지
- CSS `@import`, 동적 생성 스타일, Shadow DOM의 특정 경로
- 페이지 자산 크기가 설정된 예산을 넘는 경우
- 드로잉 캔버스가 외부 이미지를 사용해 tainted 상태가 된 경우

이런 상황을 **실패·부분 보존**으로 기록하는 것이 무조건 성공처럼 보여 주는 것보다 중요하다. 정적 DOM이 남았다고 모든 표시 요소가 완전히 보존됐다고 할 수는 없다.

## 7. Capture — Chrome CDP로 기록하는 것

### 7.1 왜 Chrome Debugger를 선택했나

페이지의 JavaScript `fetch`만 덮어쓰면 일부 네트워크 요청이 훅 적용 이전에 일어날 수도 있고, 이미지·CSS·브라우저가 직접 수행한 요청을 모두 포괄하지 못할 수 있다. 그래서 초기 네트워크 기록은 브라우저의 **Chrome DevTools Protocol Network 영역**을 활용한다.

구조는 다음과 같다.

```text
chrome.debugger.attach(tabId)
         │
         ├─ Network.enable
         ├─ Page.enable
         │
         └─ Network events
             ├─ requestWillBeSent → 요청 메서드 관찰
             ├─ responseReceived → URL / status / MIME / 리소스 유형
             ├─ loadingFinished → getResponseBody 요청
             ├─ webSocketCreated
             ├─ webSocketFrameSent / Received
             └─ webSocketClosed
         │
         ▼
    수신 리소스 및 이벤트 버퍼
         │
         ▼
chrome.debugger.detach(tabId)
```

**핵심:** CDP 자체가 브라우저 내부 모든 것을 무제한 보관해 주는 마법이 아니다. 대상 페이지에서 실제 발생했고, 디버거가 기록할 수 있었고, 제한 크기 안에 들어온 데이터를 수집한다.

### 7.2 요청·응답에 대해 남기는 정보

현재 `capture.js`는 요청 ID를 기준으로 **URL, 요청 메서드, 리소스 유형, HTTP 상태, MIME, 응답 본문**을 기록하는 경로를 가진다. 응답 본문은 `Network.getResponseBody`로 얻으며 텍스트 또는 Base64 인코딩된 데이터일 수 있다.

용량 제한도 구현돼 있다.

| 항목 | 소스 기준 기본 제한 |
| --- | --- |
| 세션의 HTTP 응답 본문 총량 | 28MiB |
| HTTP 응답 본문 하나 | 3MiB |
| 기록 대상 리소스 건수 | 최대 400개 수준 |
| WebSocket 1개 이벤트의 문자열 | 512KiB 이하 |
| WebSocket별 이벤트 | 최대 400개 |
| 종료 전 비동기 본문 수집 대기 | 최대 약 4.5초 |

코드가 이런 한도를 둔 이유는 **아카이빙 자체가 브라우저 자원을 모두 사용해 중단되는 상황**을 막기 위해서다. 하지만 이 한도가 실제 모든 사이트에서 충분하고 최적이라는 성능 수치는 확보되지 않았다.

### 7.3 WebSocket은 정적 API 응답과 다르다

WebSocket은 요청 하나, 응답 하나로 끝나지 않는다. 연결 이후 시간에 따라 수신·송신 프레임이 계속 쌓인다. 그래서 현재 구현은 URL, 이벤트 방향, opcode, 메시지 데이터, 상대 시간 정보를 별도로 저장한다.

오프라인 재생에서는 기록된 수신 프레임을 비슷한 간격으로 이벤트화한다. 이때 **서버 자체의 상태**나 기록하지 않은 다른 클라이언트의 행동이 되살아나지는 않는다. 송신 메시지를 기록하더라도 실험적 재생기가 실제 서버의 모든 상태 전이·응답 계산을 수행하지 않는다.

### 7.4 개인정보에 대한 착각을 피하기

현재 기록기는 **쿠키 저장소를 직접 순회하거나, HTTP Authorization 요청 헤더와 POST 요청 본문을 아카이브 데이터로 명시적으로 수집하는 방식은 사용하지 않는다**. 그렇다고 저장 파일이 자동으로 민감정보 없는 파일이 되는 것은 아니다.

가령 수신된 JSON API 응답 자체에 사용자명·프로필·개인 메모·개인화 정보·비밀이 포함되면 **응답 본문은 아카이브에 남을 수 있다**. WebSocket 메시지에도 마찬가지다. 페이지 DOM의 일반 입력 필드 값 역시 일부 복제된다.

따라서:

- 비공개 사이트는 아카이빙 대상을 신중하게 선택한다.
- 저장한 HTML을 퍼블릭 GitHub에 무심코 올리지 않는다.
- 공개 전에는 기록 데이터에 개인·인증 관련 내용이 포함되지 않았는지 확인한다.
- 앞으로는 **응답 본문 마스킹·도메인별 제외·민감 필드 필터·암호화 저장** 등을 도입할 필요가 있다.

## 8. Replay — 오프라인에서 다시 움직여 보려는 실험

### 8.1 기본값은 정적 보존

웹사이트 원본 코드를 무조건 다시 실행하면, 의도하지 않은 요청을 발생시키거나 저장된 DOM을 깨뜨리거나 다른 시점의 콘텐츠를 만들 수 있다. 그래서 뷰어에서는 기본적으로 **기록한 화면을 정적으로 보여 주는 모드**를 사용한다.

원본 JavaScript는 수집 단계에서 기록하되, 정적 모드에서는 바로 실행하지 않는다. 사용자에게 '원본 JS 재생 (실험)'이라는 별도 선택을 제공했다.

### 8.2 fetch 응답 대체

실험 모드의 런타임은 `window.fetch`를 가로채 저장된 응답을 찾는다. **HTTP 메서드 + 정규화 URL**을 기준으로 기록과 대조하고 `Response` 형태로 결과를 반환한다. 없는 요청은 실패로 처리한다.

```text
원본 앱: fetch("/api/products")
                │
                ▼
       Loadit Offline fetch
                │
        저장된 요청 기록 검색
                │
      ┌─────────┴─────────┐
      ▼                   ▼
  일치 기록 있음       기록 없음
      │                   │
 Response 반환       네트워크 실행 대신 오류
```

중요한 한계: 같은 URL·메서드로 여러 차례 요청이 들어오는 앱은 시점·본문·인증 상태에 따라 서로 다른 응답을 돌려받을 수 있다. 현재 구현은 기록된 응답을 순서대로 사용하는 간단한 정책을 사용하므로, 모든 API에 대해 **결정론적 완전 재생**이 성립한다고 볼 수 없다.

### 8.3 XHR 대체

`XMLHttpRequest`의 일반적인 이벤트 상태를 흉내 내는 `OfflineXHR` 클래스가 있다. `open`, `send`, `setRequestHeader`, `getResponseHeader`, `readystatechange`, `load`, `error`, `loadend` 등 일부 동작을 지원하려는 코드다.

하지만 표준 XHR의 모든 세부 조건·전송 특성·타임아웃·스트리밍·동기 호출을 정확히 재현하는 구현은 아니다. **호환성 테스트가 필요한 실험적 폴리필**로 보는 것이 타당하다.

### 8.4 WebSocket 재생

`OfflineWebSocket`은 가짜 연결 객체를 만들고 저장한 수신 이벤트를 시간에 따라 `MessageEvent`로 내보낸다. 실서버와 새로운 연결을 만드는 것이 아니라 **기록의 재생**이다.

따라서 재생 중 사용자가 새로운 메시지를 보내더라도, 그에 대한 서버의 새로운 결과를 계산할 수는 없다. 채팅, 주식, 대시보드, 게임처럼 사용자 행동에 따라 서버 상태가 달라지는 앱은 **기록 당시의 일부 흐름만** 보여 줄 수 있다.

### 8.5 페이지 전환과 샌드박스

`viewer.html`은 `pages[]`의 HTML을 `iframe.srcdoc`에 넣어 표시한다. 내부에서 링크를 클릭하면 해당 iframe의 런타임이 `postMessage`로 부모 뷰어에 URL을 전달하고, 부모 뷰어가 저장된 페이지 색인에서 해당 URL을 찾는다.

```text
iframe 내부 링크 클릭
       │
       ▼
postMessage({ loadit: "navigate", href })
       │
       ▼
부모 뷰어의 pages URL index
       │
       ├─ 저장된 URL → frame.srcdoc 교체
       └─ 없는 URL → 아카이브에 없다는 안내
```

iframe은 `sandbox="allow-scripts"`로 구성되고 별도로 `allow-same-origin`을 주지 않았다. 이는 페이지 스크립트가 부모 뷰어의 동일 출처 권한을 쉽게 얻지 못하도록 하기 위한 장치다. 원본 페이지 복원과 보안 격리 사이에는 긴장이 존재하므로, **샌드박스가 있다는 이유만으로 모든 악성 입력에 안전하다는 보증을 해서는 안 된다**.

## 9. 한 개의 HTML을 만들면서 생긴 기술적 타협

### 9.1 리소스를 Data URL로 넣으면 파일이 커진다

이미지·폰트·미디어를 HTML에 포함하면 외부 폴더가 없어도 되는 장점이 있지만 Base64 인코딩 등으로 용량이 증가한다. 수십 개 페이지와 큰 이미지를 모두 한 파일에 담으면 메모리와 로딩 비용이 커진다.

현 구현은 **페이지별 리소스 제한, 단일 리소스 제한, 네트워크 캡처 제한, 전체 산출물 제한**을 도입했지만, 전역 중복 자산 제거·스트리밍 ZIP 수준의 효율화는 구현하지 않았다.

### 9.2 정적 보존과 완전 실행 재현은 다르다

HTML·CSS·이미지의 시각적 재현만 필요하다면 스냅샷이 상대적으로 유리하다. 그러나 SPA의 라우터, 상태 관리, 이벤트 루프, 라이브 데이터, 서버 계산까지 되살리려면 더 깊은 재생기가 필요하다.

현재 프로젝트는 이 간극을 없앤 것이 아니라, 그 간극을 다루는 **두 모드의 초기 기반**을 마련한 상태다.

### 9.3 단일 파일을 선택하면 버전 관리도 달라진다

산출물이 한 HTML이면 배포·이동·보관은 간단하지만, 페이지 하나만 교체해도 파일 전체를 다시 생성해야 한다. 차후 개선 후보는 다음과 같다.

- 동일 자산의 전역 content hash 기반 dedupe
- 페이지별 해시·출처 URL·보존 시각·검증 결과를 포함하는 manifest
- 변경 페이지만 재캡처하고 전체 HTML 재패키징하는 기능
- 선택한 페이지 부분만 추출하거나 내보내기
- 동일 URL의 다른 캡처 시점 비교(diff)
- 장기간 보존을 위한 형식 버전 정책

이 항목들은 **향후 설계 제안**이며 현 버전에서 구현 완료한 기능이 아니다.

## 11. 코드에서 읽을 수 있는 위험과 개선 순서

### P0 — 먼저 확인하거나 고쳐야 할 것

1. **Chrome 실제 설치 및 전체 E2E 검증**  
   정적 문법 검사를 통과하더라도 Chrome API 경로와 실제 페이지 권한에서 실패할 수 있다. 최초로 사용자 환경에서 부하 없는 공개 테스트 사이트를 활용해 설치·기본 다운로드·2페이지 아카이빙·HTML 열기를 검증해야 한다.

2. **MV3 서비스 워커 수명과 장시간 작업 복구**  
   현재 비동기 캡처를 메모리 상태에서 실행하므로 브라우저 수명 정책에 따른 중단·부분 파일·상태 불일치 가능성을 확인해야 한다. 장기적으로 작업 체크포인트와 영속 큐를 도입할 필요가 있다.

3. **캡처 데이터의 민감 정보 관리**  
   API 응답 본문·WebSocket payload·일반 폼 값에 개인정보가 남을 수 있다. 공유 전 검사, 민감 URL 제외, 도메인 허용 목록, 응답 마스킹이 필요하다.

4. **외부 리소스와 원본 JS의 실행 경계 검사**  
   CSP·sandbox·URL 정규화·HTML 삽입·`postMessage` 이벤트가 예상치 못한 다른 출처 접근 또는 외부 네트워크 요청을 허용하지 않는지 악의적 입력으로 테스트해야 한다.

5. **오프라인 재생 기능의 브라우저별 재현성**  
   `fetch`·XHR·WS의 표면 API만 재현한다고 표준 전체를 구현한 것은 아니다. 수신 프레임 타이밍, 중복 API 요청, Base64 바이너리, 모듈 스크립트, 상대 URL, 오류 상태를 각각 독립적으로 시험한다.

## 12. 선택하지 않은 설계와 이유

### Node.js 서버를 필수로 두지 않았다

처음의 고급 아카이빙 발상에는 확장 + Node 크롤러 + 네이티브 메시징 같은 대안도 있었다. 그러나 현재 프로젝트에서 사용자는 **HTML/CSS/JavaScript만 사용**하길 명시했다. 그래서 이번 버전은 Chrome 확장과 브라우저 API 안에서 구현을 시작했다.

이는 Node가 절대 불필요하다는 주장이 아니다. 대용량 장기 수집·파일시스템 스트리밍·영속 큐는 별도 프로그램이 유리할 수 있다. 다만 **현재 구현의 배포와 실행에 Node를 필수로 요구하지 않는다**는 점이 선택의 핵심이다.

### 일반 다운로드와 웹사이트 보존을 한 엔진으로 섞지 않았다

파일 하나를 내려받는 것과 여러 페이지에서 DOM·자산·네트워크 이벤트를 모으는 것은 문제 유형이 다르다. 그래서 UI는 통합하되 내부 구현은 분리했다. 한 기능의 제약이 다른 기능의 목표를 바꾸지 않도록 하기 위함이다.

### 원본 JavaScript를 기본 실행하지 않았다

정적 아카이빙은 우선 '수집 시점의 화면'을 보관한다. 원본 스크립트를 실행하면 기록 당시의 장면에서 벗어날 수 있다. 따라서 실험 모드를 별도로 마련했다. 기록된 동작을 재현하고 싶은 사용자에게는 길을 열되, **아카이브 기본 동작을 불안정한 재실행에 의존시키지 않으려는 선택**이다.

### 모든 것이 완벽히 보존된다고 주장하지 않았다

서버가 브라우저에 주지 않은 데이터, 보안 정책 때문에 관찰할 수 없는 정보, 제한을 넘어서는 대용량 데이터는 저장할 수 없다. 제품의 가치는 불가능한 약속보다 **어디까지 수집했는지 설명할 수 있는 기록**에서 나온다.

## 13. 개발·운영 시나리오와 사용성 관점

### 13.1 개발자 · 학습자

새 라이브러리의 문서나 사례를 조사할 때 파일 한 장보다 하위 페이지 간 관계를 저장하는 편이 유리하다. 여러 문서 화면을 한 HTML에 묶으면 다음번에 다시 자료를 열 때 찾아다닐 필요가 줄어든다. 단, 이 사용 사례는 사이트 저작권과 이용 조건을 존중해야 한다.

### 13.2 디자이너 · 프런트엔드 제작자

참고할 랜딩 페이지를 여러 개 모아 두고 어떤 페이지에서 특정 요소를 봤는지 기록하기에 유용하다. 스크린샷과 달리 선택 가능한 텍스트·레이아웃 일부를 남길 수 있다. 단, 렌더 픽셀 완전 일치나 모든 폰트 포함은 아직 보장되지 않는다.

### 13.3 기록을 오래 보존하려는 개인

메모를 작성하고 즉시 TXT 또는 GitHub 새 파일로 남기는 빠른 저장 흐름과, 웹페이지를 하나의 문서로 보관하는 흐름을 결합할 수 있다. 여기서 핵심은 **정보를 복잡한 서비스 계층에만 맡기지 않고 사용자가 직접 읽을 수 있는 파일로 내보낸다**는 것이다.

### 13.4 UI 원칙

- 복잡한 개발 도구여도 기본 진입은 **주소 입력 → 저장**으로 단순화한다.
- 다운로드/사이트 보존/메모는 기능별로 분리해 인지 부담을 줄인다.
- 오류는 파일이 없거나 불완전하다는 사실을 감추지 않고 표시한다.
- 고급 기능은 선택적으로 노출한다.
- 저장 결과가 장기간 재사용될 것을 염두에 둔다.

## 14. 유지보수·릴리스 체계 제안

실제로 관리 가능한 릴리스가 되려면 다음을 지켜야 한다.

1. **버전 단일화:** `manifest.json`, 팝업 하단, README의 버전 일치.
2. **원본과 산출물 구분:** 확장 소스와 아카이빙 결과물 혼동 방지.
3. **커밋 근거:** 큰 기능을 한 문장으로 끝내지 말고 변경 파일·범위를 명시.
4. **테스트를 완료의 일부로:** Chrome에서 동작할 때만 '실행 검증 완료'라고 기록.
5. **테스트 자산 보존:** 픽스처·실행 환경·실패/성공 로그와 스크린샷을 축적.
6. **회귀 방지:** 버그 수정 전에 실패를 재현하고, 수정 뒤 동일 시험 통과.
7. **데이터 보존 정책:** 민감 정보·개인화 API 응답·공유 가능한 파일을 분리.
8. **릴리스 노트:** 기능 추가/변경/알려진 제한/검증 환경을 명시.

이 문서화 이후에도 실제 Chrome 환경에서 검증 기록을 채우지 않는다면 릴리스 성숙도를 '안정판'으로 올려서는 안 된다.

## 15. 현재 결과물과 정직한 결론

**완료된 것으로 확인할 수 있는 것**

- GitHub 저장소에 다운로드·빠른 메모·GitHub 텍스트 생성·다중 페이지 캡처·단일 HTML 뷰어의 소스가 존재한다.
- CDP 네트워크 기록과 제한적인 fetch/XHR/WebSocket 오프라인 재생을 위한 코드가 존재한다.
- Manifest V3, 팝업, offscreen document, 테스트 사이트 등 기능을 연결하는 파일 구조가 구성됐다.
- 초기 구현, 이미지 병렬화, 네트워크 재생 고도화 과정이 각 커밋에 남아 있다.
- 소스 코드의 일부 문법/구조 검사는 이전 작업에서 실행됐다.

**아직 완료라고 말하면 안 되는 것**

- 실제 Chrome 설치부터 저장된 HTML을 여는 전체 작업의 **완전한 E2E 검증**.
- 여러 실제 SPA/동적 웹사이트를 대상으로 한 보존 충실도 검증.
- 장시간 작업의 MV3 서비스 워커 중단 대응.
- 모든 응답·실시간 동작·Service Worker·IndexedDB까지 포함하는 완전 복제.
- 자동 민감정보 제거와 안전한 파일 공유 보증.
- 성능 우월성, 100% 완성도, 리소스 누락률 0% 등 정량적 주장.

이 프로젝트의 현재 도달점은 **순수 HTML/CSS/JavaScript로 구현한 통합 확장프로그램의 초기 프로토타입과, 정적 보존을 넘어 네트워크 기록·오프라인 재생까지 시도한 실험적 아키텍처**다.

원래의 요구를 기억할 필요가 있다. 목표는 단지 HTML 파일을 생성하는 데 그치지 않는다. **웹을 사용하면서 발견한 것들을 번거로움 없이 저장하고, 시간이 지나도 다시 읽을 수 있게 만드는 것**이다. 좋은 아카이버는 가장 화려하게 저장했다고 주장하는 도구가 아니라, **무엇을 보존했고 무엇을 잃었는지 분명하게 설명할 수 있는 도구**여야 한다.
